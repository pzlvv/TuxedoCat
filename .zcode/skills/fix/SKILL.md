when_to_use: 遇到缺陷（代码与 as-built 规格 / 契约不一致，应有行为已定义但没做到）时

产物：`specs/defects/<slug>.md`（扁平单文件，文件名即 slug，不编号、不归档、常驻仓库）。
两段各自产出即停：第一段产出评估与**先红**的回归用例，第二段产出修复与验证记录。
本流程不写 plan、不写 tasks、不设 severity。

**前置闸门（不过即拒绝，逐项指出）**：

- **定档**：本流程只服务 L1——代码与 as-built 规格 / 契约不一致，应有行为已定义、只是没做到。
  - L0（可观察效果不落任何 US / FR 的 AC，且不触契约面：笔误、样式、文案、依赖）→ 告知
    「这档不走流程，直接改」并停；
  - L2（as-built 规格定义的应有行为本身要变）→ 走需求变更路径：就地改 `docs/` 的基线 +
    代码 + 测试；基线缺失时先补基线（单独提交）再变更；
  - L3（新增 US / FR / 事件 / 契约成员 / 面板 / 宿主）→ 转 `/spec`。
- **判决**：不是缺陷（误用 / 期望行为 / 重复 / 超出范围）→ **不写文件**，说明理由并停。

步骤（第一段：评估 + 红）：

1. 定 slug：小写连字符、与缺陷同名；`specs/defects/<slug>.md` 已存在时加 `-2` / `-3` 后缀，
   并在正文引用原 slug——不覆盖既有文件。
2. 复制 `specs/_templates/defect-report.md` 到该路径，frontmatter 的 status 保持「待修」。
3. **只读代码**定位根因，写「现状 / 期望 / 不变量」；复现步骤写不清的标 `[待澄清]`（同行带
   去向链接），不留猜测。
4. 写「回归测试」：每条 `RT-n` 一个可执行用例 + 落点（测试文件与用例名）；**跑一次让它红**，
   把命令与失败断言记进「验证记录」的第一行。
5. 停：把 defect.md 交给用户确认根因与回归用例，等明确反馈。

步骤（第二段：修复 + 绿）：

6. 改代码让回归用例转绿，并跑既有回归。
7. 写「验证记录」余下行：修复后绿、既有回归、跑不了的检查写 `skipped` / `not-run` 加原因。
8. status 改「已修」，停：报告改动与证据落点（用户可见的收尾是提交，见下）。

三条硬规则：

- **评估段禁止修改任何源码**：发现该改的地方先记进「期望」，留到第二段。
- **修复段不许改「现状 / 期望」**：它是契约；分歧记进「验证记录」的备注列。
- **验证段禁止改源码**；评估里列的复现路径没真跑过时只能记「部分验证」，不许记「已修」。

边界：

- 写不出会先红的回归用例：不落 AC 的笔误级归 L0；其余说明根因尚未定位，继续评估，不许跳过
  红直接修。
- 评估发现代码才是对的、规格写错了：那是文档缺陷，直接改 `docs/` 并说明，不按本流程记「已修」。
- 提交时按 `AGENTS.md` 第 5 节写 trailer：`Flow: L1` + `Defect: <slug>`。

规则出处：`specs/README.md`（缺陷规格一节）、`AGENTS.md` 第 5 节（四档判据与闸门）。
