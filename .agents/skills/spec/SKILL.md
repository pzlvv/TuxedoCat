when_to_use: 新增能力（US / FR / 事件 / 契约成员 / 面板 / 宿主）需要版本化规格时

产物：`specs/<NNN>-<slug>/spec.md`。只做这一件事，产出即停，等人评审；评审通过前不得
进入 /plan。

步骤：

1. **定档（第一步，先于起草）**：按 `AGENTS.md` 第 5 节的四档判据判断这次改动属于哪一档，
   只对 L3 继续往下走：
   - **L0 直改**（可观察效果不落任何 US / FR 的验收标准，且不触契约面：样式、文案、配置、
     依赖、纯重构）→ 告知「这档不走流程，直接改」，停；提交信息写 `Flow: L0`。
   - **L1 缺陷修复**（应有行为已定义、只是没做到）→ 转 `/fix`（产物 `specs/defects/<slug>.md`），
     停。
   - **L2 需求变更**（as-built 规格定义的应有行为本身要变）→ 不新增 spec：定位基线（`docs/`），
     有则就地修订 FR / AC + 代码 + 测试；缺失则**先补基线**（基于代码写现状，只补本次涉及的
     行为，单独一个提交），再基于它变更；提交信息写 `Flow: L2`，停。
   - **L3 新特性**（新增 US / FR / 事件 / 契约成员 / 面板 / 宿主 / 文件格式）→ 继续第 2 步。
   - 判不清取较高档；档位可升不可降。
2. 定编号与 slug：编号取 `specs/` 与 `docs/archive/specs/` 已用最大值 +1（三位、不复用）；
   slug 小写连字符，与实施分支同名。
3. **补记模式（改动已部分实现时必走）**：先读实现 diff，反向枚举行为清单——正常路径
   之外，错误路径、竞态、中止、边界置灰是重点——FR / AC 逐条对照该清单：实现里有的
   行为必须有对应条目，也不写实现里没有的承诺。补记模式禁止双头表述（「若 plan 采用
   X 则…」）：现状已定，按实现写；待澄清只留真正未决的问题。
4. 复制 `specs/_templates/spec.md` 到 `specs/<NNN>-<slug>/`，frontmatter 的 status 保持
   「起草」。
5. 影响基线：逐条声明改动落在哪些 as-built 规格的哪些章节（只链接**已存在**的文档与
   锚点），标注新增 / 修改 / 删除；新增文档在落地前写行内代码、落地后改链接。
6. 用户场景与验收标准：每条验收标准一行式 GIVEN / WHEN / THEN，写作
   `- **AC-n**（FR-nnn）：GIVEN … WHEN … THEN …`，回指功能需求条目；不写
   「支持 / 优化 / 合理 / 尽量」这类不可判定的词。
7. 功能需求：`### FR-nnn：<标题>`（nnn 三位、不重复），只写「应该是什么样」，
   不写实现方案（那是 /plan 的事）。
8. 补齐边界与错误路径、非目标、对 docs/features/user-stories.md 的影响（新增 US 必须登记 e2e
   用例或按既有口径登记豁免；流程类改动写「无新增 US」+ 理由）。
9. 未决问题写入「待澄清」节：`[待澄清]` 必须同行带去向链接（转 ADR / 转
   [docs/architecture/open-questions.md](../../../docs/architecture/open-questions.md) / 写成非目标）；实施前必须清零。
10. 停：把 spec.md 交给用户评审，等明确反馈；提交信息写 `Flow: L3` + `Spec: <NNN>`。

规则出处：`specs/README.md`（工作流与守卫口径）、`AGENTS.md` 第 0 节（specs/ 例外与
写作规则）、`AGENTS.md` 第 5 节（四档判据与闸门）。
