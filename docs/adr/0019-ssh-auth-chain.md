# ADR-0019：SSH 接入的认证链（私钥优先、口令按需）

- 状态：已采纳
- 日期：2026-11-19
- 规格：[specs/052-ssh-key-first-connect](../../specs/052-ssh-key-first-connect/spec.md)

## 背景（Context）

「打开远程工作区」原来把口令当成表单必填项：面板一打开就是一个带口令输入框的表单，
用户必须先知道并输入口令才能点「连接」。这把 SSH 的三种认证方式压成了一种，而且要求
用户在**连接之前**就决定用哪种凭证——用户本来就不该被问他有没有私钥。

同时，凭证在仓库里是单一形态 `{ kind: 'sshPassword'; password }`，所有消费方（终端可用性、
跨工作区传输、侧栏远端文件浏览、连接池去重、重启恢复）都靠 `kind === 'sshPassword'` 判断，
「有没有凭证」与「是不是口令」两件事被写在了同一个判断里。

## 决策

1. **认证链的顺序固定为「默认私钥 → ssh-agent → 已保存的口令 → 询问用户」**，顺序只在
   `src/host/sshAuth.ts` 的 `sshAuthChain` 定义一次，其余位置一律引用它。
2. **失败分两类**：`classifySshFailure` 把「认证不成立」判为 `auth`（推进链），把不可达 /
   建链超时 / 主机密钥不一致判为 `fatal`（直接报错、不弹口令浮层）。认不出的错误一律按
   `fatal` 处理——兜底链只吃一种确定结论。
3. **加密或损坏的私钥按「该来源不可用」跳过**，不询问 passphrase（本次范围）。
4. **口令只在认证链耗尽时才问**，形态是接入面板上的模态浮层；提交失败保持浮层并回显原因，
   不设次数上限。
5. **只有口令认证成功才写连接历史**；私钥 / agent 成功不写口令字段、也不改动已有条目。
6. **凭证扩成判别联合** `WorkspaceAuth = sshPassword | sshKey`，`sshKey` 只携带身份描述
   （`keyPath` 或 `null` 表示 agent）。私钥正文与 passphrase 不落盘、不进跨进程载荷，只在
   建链那一刻从磁盘读。
7. **所有消费方以「凭证是否可用」判定**，不再区分凭证种类。
8. **连接目标的身份键包含凭证身份**（`sshAuthIdentity`：口令哈希 / 私钥内容哈希 / `agent`），
   换凭证即换连接。

## 被否决的替代方案

- **口令字段改为可选、其余不变**——面板里仍有常驻口令框，用户会被引导去输口令；
  且「有没有凭证」与「用哪种凭证」仍挤在同一个字段上，`WorkspaceAuth` 无法表达私钥身份。
- **先问口令、失败再试私钥**——口令是唯一需要人工介入的来源，放前面等于每次连接都要人参与。
- **把全部认证方式交给 `ssh2` 的 `authHandler` 自己按序试**——库的重试顺序不透明，失败后无法
  区分「这条来源不可用」与「整机不可达」，而 `auth` / `fatal` 二分是「不要为拼错的主机名去
  输口令」这条语义的全部依据。
- **凭证身份键只取种类（不含内容）**——会让「第一次输错口令、改对后重试」复用旧连接，违背
  既有的「换口令必须换连接」口径。

## 后果

- 面板首屏不再有口令输入；`sshHistoryEntry`（按去重键取含口令的整条历史）这个 IPC 成员
  随之删除——页面在任何时刻都不持有历史口令。
- 终端、跨工作区传输、侧栏远端文件浏览、重启恢复对两种凭证一致可用；凭证不可用时各自按
  既有口径拒绝并报错，文案点名「凭证不可用」。
- 落盘的 `workspace-state.json` 多出一种凭证形态；读取口径对 `sshKey` 要求 `keyPath` 字段
  显式存在（缺字段不当作 agent）。
- 本次不覆盖：加密私钥的 passphrase 交互、面板里手选私钥文件、agent 转发。这三项登记在
  [TODO.md](../../TODO.md)，不阻塞本次语义成立。
