# ADR-0012：会话独占锁用 OS 建议性文件锁

- 状态：已采纳
- 日期：2026-10
- 规格：[standalone-core.md 第 7 节](../core/standalone-core.md#7-事实归属)（会话独占锁的事实归属）、[client-connection.md 第 5 节](../core/client-connection.md#5-connection-生命周期)（连接独立、会话独占）

## 背景

specs/032 要求：同一工作区的同一会话同一时刻至多被一个宿主实例打开，争用硬拒绝。
锁落在会话数据目录、由 Core 持有，必须覆盖本地多实例与 SSH 多客户端两类形态。核心
选型问题是互斥机制：锁文件协议（文件存在性 + 内容判活）还是内核建议性锁。

会话锁的持有时长是小时级（跟会话视图生命周期走），远长于构建缓存一类的秒级锁；
持有者崩溃、被强杀是常态路径而非异常路径（宿主强杀不留给 Core 收尾机会）。在这两个
约束下，锁文件协议有结构性缺陷：

- **摘除-重建的接管存在双持有竞态**：接管者摘掉旧锁文件再建新锁的间隙，另一个接管者
  可以同样摘掉刚建的新锁、再建自己的——文件系统没有「存在即失败」的原子 CAS，两个
  接管者各自认为接管成功，双持有；这发生在锁文件脱链后 inode 仍被锁定的窗口里，
  无法靠复读根除；
- **「残缺即无主」罩不住建锁窗口**：以内容残缺判陈旧，则建锁后写 pid 前崩溃的持有者
  留下空文件，被误判无主而抢占；
- **僵尸与判活盲区**：Linux 僵尸进程 `kill(pid, 0)` 判活、Windows 上 pid 复用与
  mtime 老化各有误判面（remote.rs / config.rs 的 mtime 先例只适合秒级短临界区）。

## 决策

**互斥由 OS 建议性文件锁承担**（Unix `flock(LOCK_EX | LOCK_NB)` / Windows
`LockFileEx(LOCKFILE_EXCLUSIVE_LOCK | LOCKFILE_FAIL_IMMEDIATELY)`，`core-rs/src/session_lock.rs`
手写 FFI、零新依赖）：

- 锁的生命周期归内核：持有进程退出（含崩溃、被杀、成僵尸）即释放，接管退化为
  「再次获取」，无摘除-重建步骤，上述竞态整体消失；并发获取由内核保证至多一胜。
- 锁文件内容（单行 JSON：版本 / pid / 进程启动时刻）只作占用诊断与版本拒外，不参与
  互斥判定：解析不出版本视为损坏照常持有，版本 ≠ 1 立即释放并拒绝（fail-safe 方向
  是拒外不是抢占）。
- 句柄 Drop 只 unlock + close、不删锁文件：释放期摘文件会让并发的下一个获取者锁到
  已脱链 inode；残留文件无害，随会话目录删除自然消失（删除清单含 `.session.lock`）。
- 锁的持有者是 Core 进程内的会话实例（`Core.session_locks` 注册表）：宿主 detach /
  孤儿化只断控制连接，锁照旧持有（specs/031 的认领是同 Core 重入）；释放只随
  `drop_session` 或 Core 进程退出发生。

FFI 手写而非引第三方锁 crate（fs2 / fs4）：为两个 syscall 引依赖不值得，仓库已有
`parent_watchdog` 的 kernel32 / libc 手写先例。选 `flock` 而非 fcntl POSIX 记录锁：
fcntl 锁在进程内任一 fd 关闭即全部释放，同文件多 fd 场景语义危险；flock 按 open file
description 独立，贴合「每会话一柄」。

## 替代方案（被否决）与后果（Consequences）

被否决的替代方案：

1. **纯锁文件 + 摘除式接管（spec 原稿：`O_EXCL` + pid + 启动时刻判陈旧）**：双持有
   竞态与建锁窗口如上，会话锁小时级持锁不可容忍——已按崩溃路径评审修订否决。
2. **收紧的摘除协议（摘前复读确认 + mtime 宽限 + 摘后建失败即让）**：把竞态窗口从
   毫秒压到微秒但残余仍在，协议复杂度反而高于内核锁。
3. **fs2 / fs4 等锁 crate**：为两个 syscall 引第三方依赖。
4. **fcntl POSIX 记录锁**：进程内任一 fd 关闭即全部释放。
5. **宿主侧（TS `src/shared/history/`）加锁**：会话数据的写入者是 Core；宿主零改动
   也是 specs/032 的约束。
6. **mtime 老化判活沿用 remote.rs / config.rs 先例**：pid 复用误判、Windows 盲区、
   僵尸误判三病齐发，只适合秒级短临界区。

代价与好处：

- 好处：接管语义退化为一次非阻塞获取，无陈旧锁协议、无判活、无死锁残留；互斥仲裁
  与释放保证全部外包给内核，Core 侧只剩「获取 / 持有 / 释放」三个动作。
- 代价 1：建议性锁挡不住不协作的写者——会话数据的全部写入路径都过 Core（宿主侧
  `src/shared/history/` 的直写只发生在本实例持锁时），协作面封闭，可接受。
- 代价 2：Windows 的字节范围锁是强制的，持有期间第三方句柄读不出锁文件内容，占用
  诊断的 pid 在 Windows 上可能为 `unknown`（文案已按缺省口径处理）。
- 代价 3：锁文件残留在会话目录直到删除（历史列表、压缩归档等按后缀过滤，不受影响）。
