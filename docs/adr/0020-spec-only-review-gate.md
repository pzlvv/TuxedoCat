# ADR-0020：spec 是唯一评审面，plan / tasks / 实施 / 收敛一轮做完

- 状态：已采纳
- 日期：2026-11-20
- 规格：`specs/README.md`（工作流与生命周期）、[AGENTS.md 第 5 节](../../AGENTS.md#5-工作流)（四档入口）

## 背景（Context）

改动规格流程原本按五个 skill 串起来：`/spec` 起草、`/plan` 定方案、`/tasks` 拆任务、
`/implement` 实施、`/converge` 收敛归档，每个 skill 产出即停、等人评审。

问题是评审面被摊成了四道：spec 评审、plan 评审、tasks 评审、收敛裁决。人审一次的
信息量集中在「要做出什么样」（spec 的 US / FR / AC），而 plan 的技术路线、tasks 的拆分
与勾选顺序、收敛记录的三分类都属于同一批意图的落地细节——逐段停下等人看，只是把一次
决策切碎成四次确认，每次都要重新装载上下文。更实际的是：plan 阶段发现的方案问题往往
只能通过回改 spec 解决，tasks 阶段发现的拆分问题通常只是执行细节，收敛阶段的三分类
在实施时就该边走边判断。

ADR-0004 定下的生命周期里「每个入口产出即停等人评审」是流程节奏的默认值，不是被论证
过的约束；ADR-0006 的分档闸门只关心提交时的档位与产物，也不要求逐段评审。

## 决策（Decision）

改动规格（L3）的入口收敛为两个，**评审闸门只卡 `spec.md`**：

- `/spec`：起草到 `spec.md`，status 填「待评审」，产出即停等人评审。评审意见回到本步
  改 spec，次数不限。
- `/implement`：spec 评审通过后一次做完 plan → tasks → 实施 → 收敛 → delta 并入 `docs/`
  → 整目录归档。中途不产出即停、不等人评审；`plan.md` 与 `tasks.md` 是这一轮的过程产物。

配套约束：

- 状态机取值不变（起草 / 待评审 / 实施中 / 已收敛），但**「待评审」只要求 `spec.md`**；
  三件套齐是「实施中」与「已收敛」的门槛。docsLint 的 specs 结构组按此递进。
- 闸门不取消，改成实施内部的前置条件：待澄清项未清零不进 `/implement`；宪章检查不过先
  改方案再实施；收敛不绿不归档——不绿时把未做项回写 `tasks.md` 并报卡点，那是需要决策
  的阻塞项而不是评审。
- 实施中发现 spec 没覆盖的行为、或需要改 FR / AC 时停并回 `/spec` 补记：spec 仍是唯一
  可以改验收标准的地方，实施里不自定验收标准、不静默扩范围。
- `.agents/skills/plan`、`.agents/skills/tasks`、`.agents/skills/converge` 三个 skill
  删除，内容并入 `/implement`；缺陷修复（L1 的 `/fix`）的两段节奏不受影响。

## 替代方案（被否决）与后果（Consequences）

- **保留五段但把后四段的「等人评审」改成「自动继续」**：skill 之间的交接仍需要人重新
  触发，等价于人工点四次继续，没有减少确认次数，只是把停下换成等待。
- **保留 `/plan` 单列，只合并 tasks / implement / converge**：plan 是评审价值最低的一环
  （技术路线在 spec 的「非目标」与影响基线里已被约束），单独留一段仍然是为同一批意图再
  确认一次。
- **完全取消 plan.md / tasks.md 两个产物**：实施过程就失去可勾选的进度与宪章检查的落点，
  `/implement` 一轮变长后无法从仓库判断做到哪一步，也无法在收敛时对照「承诺了什么」。
- **代价**：单轮 `implement` 变长，出问题时要回退的粒度更大；缓解手段是 tasks 逐条勾选
  （进度可见）、收敛记录三分类（偏差留痕），以及「改 FR / AC 必须回 `/spec`」这条硬边界。
