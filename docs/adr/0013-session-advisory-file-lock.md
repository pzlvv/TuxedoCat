# ADR-0013：会话独占锁用 OS 建议性文件锁

- 状态：已采纳
- 日期：2026-10
- 规格：[docs/core/standalone-core.md 第 7 节](../core/standalone-core.md#7-事实归属)（事实归属）
  与 [docs/core/client-connection.md 第 5 节](../core/client-connection.md#5-connection-生命周期)（连接独立、会话独占），随 specs/032 落地

## 背景

specs/032 要求「同一会话同一时刻至多被一个实例打开」。锁的持有者是 Core 进程内的会话
实例，持锁时长是**小时级**（用户开着对话就可能持有几小时）；持有者会崩溃、被强杀，
也可能在宿主离场后作为孤儿（specs/031）继续持锁。spec 原稿的锁协议是「纯锁文件 +
`O_EXCL` + pid + 启动时刻判陈旧 + 摘除式接管」。

评审发现该协议对小时级持锁不可接受：

- **双持有竞态**：摘除-重建式接管里，两个接管者可以互相摘掉对方刚建的新锁——文件系统
  没有对「存在性检查 + 建文件」的原子 CAS，竞态窗口只能收窄不能根除；
- **覆盖窗口**：「残缺即无主」罩不住建锁成功与写入 pid 之间的崩溃窗口；
- **判活的平台盲区**：pid 存在性判活误挡僵尸、Windows 判活 / 启动时刻需要整套平台
  实现（`remote.rs` 的既有先例在 Windows 是按存活处理的盲区）。

## 决策

互斥交给**内核的建议性文件锁**：Unix `flock(LOCK_EX | LOCK_NB)`、Windows
`LockFileEx(LOCKFILE_EXCLUSIVE_LOCK | LOCKFILE_FAIL_IMMEDIATELY)`（手写 FFI，零新依赖，
与 `parent_watchdog` 的声明风格一致）。锁的生命周期归内核——持有进程退出（含崩溃、
被杀、成僵尸）即释放，「接管」退化为「再次获取」，并发尝试由内核仲裁至多一胜。
锁文件内容（格式版本 / pid / 进程启动时刻）只作占用诊断与版本拒外（无法识别的版本
视为有效占用、拒外方向 fail-safe），不参与互斥。

实现落点：`core-rs/src/session_lock.rs`（原语 + Core 内注册表 + 变更守卫），
测试矩阵 `core-rs/src/session_lock_tests.rs`（自 spawn 双进程 harness）。

## 替代方案（被否决）与后果

- **收紧的摘除协议（摘前复读确认 + mtime 宽限 + 摘后建失败即让）**：把竞态窗口从毫秒
  压到微秒但残余仍在，协议复杂度反而高于内核锁。否决。
- **fs2 / fs4 等锁 crate**：为两个 syscall 引第三方依赖；仓库既有手写 FFI 风格零依赖
  可达成。否决。
- **fcntl POSIX 记录锁替代 flock**：fcntl 锁在进程内任一 fd 关闭即全部释放（同文件多
  fd 场景语义危险）；flock 按 open file description 独立，贴合「每会话一柄」。否决。
- **宿主侧（`src/shared/history/`）加锁**：会话数据的写入者是 Core，宿主只在持有实例
  的窄场景直写，彼时锁必在本 Core 手里；宿主零改动也是 spec 约束。否决。
- **mtime 老化判活沿用 `remote.rs` 先例**：pid 复用误判、Windows 盲区、僵尸误判三病
  齐发，只适合秒级短临界区。否决。

后果与代价：

- 互斥依赖内核与文件系统语义：锁文件所在卷必须支持建议性锁（本地盘 / SSH 远端本地盘
  均成立；网络盘不在覆盖范围——specs/032 的锁只在会话数据所在机器内有效）。
- **Windows 语义细节**：锁住的字节范围会挡住其他句柄对它的读取——锁文件的读写必须
  走持锁句柄自身；诊断读取失败按 `unknown` 退化（spec 边界明文）。
- 建议性锁不防「不读锁的进程」：独占是对本产品 Core 之间的约定，外部工具改写会话数据
  不在防御范围（与「锁文件被外部删除不防御」同级，spec 边界明文）。
