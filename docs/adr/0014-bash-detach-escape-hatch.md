# ADR-0014：Bash 的 detach 定位为管辖豁免开关而非执行模式

- 状态：已采纳
- 日期：2026-10
- 规格：[docs/features/bash-detach.md](../features/bash-detach.md)（闸门 / 豁免语义 / 授权分级 / 两面文案），随 specs/034 落地

## 背景

模型在 Bash 命令里手写 `nohup` / `&` / `setsid` 等写法时，进程脱离 `bash -c` 这个被
工具追踪的子进程：后台任务注册表、完成通知、abort 杀树、会话 `background` / `idle`
事实全部看不到它。业界对照：

- **Claude Code**：`run_in_background` 体系完整（任务 id、输出文件、完成通知、停止），
  但后台命令有运行时长封顶（默认 30 分钟、至多 2 小时，到点停并通知）——超长任务
  事实上被生态推向 `nohup` / systemd 逃逸，逃逸后零追踪；
- **dsh**：每条命令自始注册为 job（前台超时转后台是同一个 job id，`job_output` /
  `job_list` / `job_kill`），架构上消解了「转后台才建档」的空档，但对自脱离构造
  同样不拦不追；
- **OpenCode**：Bash 工具至今没有模型侧后台字段，后台化是宿主行为（steer 转后台、
  activity pill）；管道 EOF 与进程退出的结算之争最终倒向「按进程退出结算」。

即：对自脱离构造「设闸 + 授权」在业界没有先例，设计需要在没有对照的情况下定形态。

## 决策

`detach` 字段是**管辖豁免开关**，不是执行模式：设为 `true` 表示「该命令的进程脱离
工具管辖」——命令原样执行，不进后台任务事实、abort 不杀、会话结束后继续存活；
豁免要生效还须命令真的命中后台化构造（字段否则惰性）。缺省 `false` 时命中构造
直接失败并给出路由判据（错误即教学）；`detach: true` 且命中构造按危险操作参与
权限分级——`manual` / `risk` 弹确认框，**`auto` 放行且零模态可见**（无徽标、无
回显），零可见是明示决策。授权不做持久化（无「本会话总是允许」）。

## 替代方案（被否决）与后果

- **工具级 detach 执行模式**（由工具代为 detached spawn 并持句柄登记后台任务）：
  语义上「更可追踪」，但它把「要逃离管理」的命令重新纳入管理——与 detach 的语义
  自相矛盾，且 Windows（`DETACHED_PROCESS` / `CREATE_NEW_PROCESS_GROUP` /
  breakaway）与 POSIX（`setsid`）的分离行为要各自验证，成本与收益不成比例。
- **进程表扫描反推归属**（按命令行猜「这个 pid 是不是本会话逃出去的」）：违反
  [架构原则第 7 节](../architecture/principles.md#7-一份事实只有一个写入点)
  （禁止从投影反推事实），误判不可控，不做。
- **auto 模式做徽标 / 结果回显**：`auto` 是用户「什么都没问过」的显式声明，破坏性
  命令（`dd` / `mkfs`）在 auto 下同样零可见；为 detach 单独立可见性破坏对称性。
  接受零可见并在此留痕；如需要另起 spec。
- **持久授权白名单**：范围外，如需要另起 spec。

后果：代价是 auto 模式下用户对脱离零感知、豁免进程只能由用户自行回收（taskkill /
kill）；好处是误用被第一轮失败拦住并教学、真豁免要过授权、事实模型不撒谎——
工具只声明它真正拥有的事实。
